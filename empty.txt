1. EXECUTIVE SUMMARY
------------------------------------------------
Overall: the backend is real, database-driven, internally consistent and well
tested. All 64 routes are reachable and behave correctly for anonymous, student and
admin callers. 541 tests pass, 0 fail, 11 skipped (by-design); manage.py check is
clean; there is no migration drift; the OpenAPI schema generates with no warnings
and matches the committed docs/openapi.yaml exactly.

No CRITICAL security defect was found. Privilege separation, IDOR protection, Stripe
signature/idempotency/amount checks and the secure viewer all hold under test.

The gaps are WORKFLOW-SHAPE gaps, not bugs:
  G1  The Admin workflow step "Make Decision: Immediate Access / Payment Required /
      Keep Pending" does not exist as a per-registration decision. Registration
      approval is account-level (pending -> active / rejected). Whether a course is
      free, manually approved, or paid is a COURSE property (Course.access_mode).
      "Immediate" is only reachable as a per-student, per-course admin grant
      (POST /api/admin/access/grant/). "Payment required per student" has no
      equivalent. (PARTIAL)
  G2  The URL layout does not match the target: no api/admin/login/, api/admin/course/
      (plural "courses/" exists), api/admin/students/ (it is "users/" +
      "registrations/"), api/admin/notifications/ (shared /api/notifications/),
      and the student area is not fully under api/student/ (course, viewing,
      payment, notifications, profile live elsewhere).
  G3  No lessons model; "course content" = PDF resources only. No course "unpublish"
      (only archive). Course update is PATCH only (PUT -> 405).
  G4  "Zoom validation" in the viewer: there is no zoom parameter. Render width is a
      server setting; any ?zoom= is ignored. (Not a vulnerability; feature absent.)
  G5  No frontend exists in the workspace (no frontend/ dir), so every frontend
      dependency is UNKNOWN. /student/pending etc. are frontend routes the backend
      can only support through status codes/fields.

Counts: 64 unique paths, 76 HTTP operations (11 public, 8 any-authenticated,
14 student, 43 admin). 2 more routes (schema, docs) exist only when
API_DOCS_ENABLED (default = DEBUG).

11. COURSE ACCESS AUDIT
------------------------------------------------
Central function: access.services.evaluate_access(student, course, record=_UNSET) ->
AccessDecision(state, allowed, expires_at, access_id). It is the ONLY place that decides
"allowed". Callers: viewing.permissions.HasCourseAccess (viewer), CourseAccessSerializer,
access_states_for (course catalogue, N+1-safe), request_course_access, create_checkout.
No duplicate access logic found in unrelated views.
Course.status!=published OR student not approved OR role!=student  -> "unavailable" (deny).
CourseAccess.status: pending | active | rejected | revoked (+ derived expired).
Derived client states: granted, pending, requestable, payment_required, expired, rejected,
revoked, unavailable. Mapping to the brief: pending=pending; payment_required=payment_required;
active=granted; expired=expired; suspended = student account suspended -> unavailable (and
JWT rejected earlier); no per-course "suspended" state (revoked is the equivalent).
Verified: expiry boundary (X1), payment-source access with duration (P8), revoke on full
refund (suite), archived course -> unavailable (code), renewal path for paid courses (X3).

32. MEDIUM ISSUES
------------------------------------------------
M1  Session state is ONE Redis key per user (eduvault:session:<user_id>). Logout, password
    change or suspension on one device ends the session for every device (A15: after a second
    login/logout the first admin session returned 401). Also the single key means devices share
    one inactivity window. Fix idea: key the session by token jti/session id.
M2  Admin workflow step "Make Decision" (Immediate / Payment Required / Keep Pending) is not a
    registration-level feature (G1). Needs a product decision before Phase 2: either keep
    course-level modes and add a per-student/per-course "decision" endpoint, or redefine the
    workflow around course modes.
M3  First-time admin 2FA enrolment needs only the admin password: if an admin account exists
    with two_factor_enabled=False, anyone who knows the password can enrol their own
    authenticator and obtain tokens. Mitigations: provision TOTP out-of-band / require an
    existing admin to enable it / invite token.
M4  Login lockout is keyed by e-mail only (5 failures -> 15 min), so a third party can lock a
    known account (including an admin) out indefinitely by repeating failures. IP is not part
    of the key. (Throttles are per-IP, which helps only partly.)
M5  Admin notifications are PARTIAL: the endpoint works, but nothing creates admin-targeted
    notifications (new registration, access request, payment) - admins only get security
    notices - so the "admin notifications" target has no useful feed.
M6  URL layout differs from the required target (G2). Pure rename work, but breaking.

33. LOW ISSUES
------------------------------------------------
L1  PUT on course not supported; no course unpublish; no lessons (G3).
L2  Admin can grant access on a draft/archived course (AccessGrantSerializer uses Course.objects.all()); harmless (viewer evaluates as unavailable) but leaves stray records (probe R5 201).
L3  Rejected registration is terminal: re-approve returns 409; there is no re-open. Only ACTIVE users can be suspended.
L4  Every checkout click creates a new pending Payment and Stripe session (no reuse of an open one) (P1b).
L5  Stripe webhook route uses default AnonRateThrottle (60/min/IP); a burst could return 429 (Stripe retries). Consider exempting.
L6  An admin can suspend another admin; no "last active admin" protection.
L7  POST /api/accounts/register/ returns 409 EMAIL_ALREADY_REGISTERED (account enumeration; login/forgot-password do not leak).
L8  Viewer re-reads the whole PDF per page and renders synchronously; fine at current limits, watch under load.
L9  API docs (schema/docs) disabled when DEBUG off; if wanted in staging, must be flagged on explicitly.
L10 Registration detail returns profile only (no related access/payment summary).
L11 Dev .env uses locmem cache: lockout, OTP and sessions are per-process and reset on restart; make sure production uses Redis (settings default would otherwise silently weaken security).
L12 Two-factor challenge token is replayable within its 300 s window (still needs a valid TOTP/backup code).

  True): `python manage.py issue_admin_2fa_enrollment <admin-email>`. Signed, stateless, 24 h (ADMIN_2FA_ENROLLMENT_CODE_HOURS),
  bound to the user and password hash, dead once 2FA is enabled or the password changes. Wrong/missing code -> 401
  INVALID_TWO_FACTOR_CODE, audited (auth.2fa.failed), counts toward the 2FA lockout. Another admin's code is useless.
  The command refuses students and already-enrolled admins.
- Replay: an accepted TOTP code is single-use (cache add, ~2 min). Tested.
- Backup codes: 8, keyed-hash stored (64-hex), one-time atomic claim; reuse -> 401. TOTP secret Fernet-encrypted at
  rest (stored value != secret, tested). Suspended admin: challenge verify 401, login 403.
- Students are never put through TOTP (tested).
Contract change: setup accepts an extra field `enrollment_code`. Documented in FRONTEND_HANDOFF.md and OpenAPI.

8. SESSION / TOKEN STATUS: PASS (needs Redis in production, see 20)
================================================
- Each sign-in = its own session: JWT claims `sid` (device) and `ep` (per-user epoch). Inactivity key per (user, sid).
- Logout ends only that device (tested with two devices). Inactivity expiry is per device (tested).
- Password change/reset and suspension blacklist all outstanding refresh tokens AND bump the epoch, so every access
  token of every device dies immediately (tested). The device that changed the password gets fresh tokens.
- Tokens without sid/ep (not issued by the login flow) are rejected.
- Access 15 min, refresh 7 days, rotation + blacklist-after-rotation. Expired, garbage, access-as-refresh, logged-out,
  suspended-user refresh tokens all -> 401 INVALID_REFRESH_TOKEN (tested).
- Reuse detection: replaying a rotated (blacklisted but validly signed, unexpired) refresh token ends that device's
  session, including the newly issued token, and writes audit event auth.refresh.reuse_detected (token never logged;
  only the first 8 chars of the session id). Other devices are unaffected (tested).

================================================
- Key = (email, client IP) with LOGIN_MAX_ATTEMPTS (default 5) -> 429 ACCOUNT_LOCKED for LOGIN_LOCKOUT_SECONDS (15 min).

20. REMAINING RISKS
================================================
1. Production MUST run Redis. Sessions, epochs, lockout counters, TOTP replay marks live in the cache. With the dev
   locmem cache they are per-process and reset on restart. Epoch keys have no TTL: configure Redis eviction so they are not
   evicted; if lost, the safe failure is that all tokens are rejected (users sign in again), never a bypass.
2. Email-wide lock backstop (20 failures within 15 min across IPs) can still be abused to lock a known e-mail for
   15 minutes; accepted trade-off against distributed brute force.
3. 2FA challenge token (5 min) is replayable within its window; it still needs a valid, now single-use, TOTP/backup code.
4. Enrollment code is reusable until 2FA is enabled, the password changes or it ages out (stateless by design so the CLI
   works with any cache); treat it like a password and hand it over out of band. First admin created with
   `createsuperuser` must run the command once (documented).
5. Concurrent refresh with the same token (two tabs) is treated as reuse and ends that device's session.
6. Webhook route still inherits the default anonymous throttle (60/min/IP). Admin can suspend another admin (no last-admin
   guard). POST /accounts/register/ reveals whether an e-mail exists (409).
7. NOT TESTED: PostgreSQL, real Redis, live Stripe, S3 storage, Swagger page rendering.
8. Out of scope by instruction: admin notifications, course PUT/unpublish.
